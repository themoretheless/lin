# Pre-synchronized-prefix RWF_DSYNC I/O hypothesis

No production Rust source, WAL codec, record bytes, quota or sync mode changes. This standalone Linux GNU probe compares the existing write-all + fdatasync primitive with pwritev2(offset=-1,RWF_DSYNC) only after an explicitly fully synchronized valid WAL prefix. Linux documents RWF_DSYNC as the per-write O_DSYNC equivalent applying only to the written data range; it does not cover arbitrary earlier dirty writes. Offset -1 uses and updates the descriptor position. Source: https://man7.org/linux/man-pages/man2/pwritev2.2.html. No torn-write atomicity claim is made.

The range limitation is a hard precondition, not a proposed relaxation of Full durability. Production integration would separately require a proven prefix-durability state across open, Normal writes, batches, failures and fallback; this probe cannot qualify that integration. Unsupported RWF_DSYNC fails instead of being counted as a win or silently using another method.

Actual canonical frames are generated by the unchanged Lin append_record encoder. Fixtures use32real scalar or default-width Doc rows with deterministic0.25/-0.0vectors. Targets: scalar UPDATE,Doc UPDATE,Doc DELETE,one-child UPDATE Batch in Full mode, each at1and32commits per fresh file. Controls: scalar and Doc UPDATE in Normal mode, likewise1and32commits. All12cases retained; single-commit latency and32-commit batch averages are separate contracts. No warmup or post-hoc startup-sample trimming. Fixture/name/prefix sync, encoding, replay/full-row model, exact-byte/file-position/length checks, intentional CRC-corruption rejection and cleanup are outside the measured write loop. Full includes its barrier. No checkpoint/DB execution/peer/RSS/power-loss qualification is claimed.

Plan: two six-pair series with baseline/control same executable and identical write+sync method; candidate chooses only the RWF_DSYNC Full path.
