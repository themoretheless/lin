# Exact BitSet cardinality: correctness-qualified prototype, timing pending

Frozen production source is recorded in input-provenance.json. Public Row remains exactly BTreeMap<String, Cell>. This is a new representation hypothesis, separate from the previously qualified narrow prefix emptiness check: add one private usize cardinality to BitSet; increment/decrement only on actual bit transitions, retain correct count through growth and clone, update intersection and union counts, and make count/is_empty constant-time. Existing bitmap promotion at32 scalar posting members is retained; no new automatic bitmap policy is added.

The independent BTreeSet model passes against both original and candidate implementations:14336 state transitions across capacities0/1/63/64/65/1024/65537, repeated insertion/removal, sparse positions beyond100k, asymmetric AND/OR, idempotent self operations through clones, empty states, enumeration and membership checks. Candidate library plus exec, partial-index mutation, prepared GROUP BY and transaction tests:192 passed,2 ignored. A deliberate missing removal decrement is caught by the model. Raw logs and commands retained. Every source file restored to its pre-experiment SHA256; production code is unchanged.

Performance is not qualified. The added word changes opaque BitSet/PostingList memory layout and increases per-posting metadata. Maintaining cardinality adds work to writes; combining popcount with AND/OR may inhibit vectorization, particularly when no subsequent count is requested. The next gate must compare actual count-heavy and mutation-heavy workloads, both operand orders and unequal capacities, sparse/empty/dense distributions, small/large bitmaps, allocation/layout/RSS, and an unchanged control. Existing prefix-emptiness and vectorized count implementations remain controls; do not accept the prototype only because count alone becomes faster. Follow with full-engine native/Full durable and read controls before any rollout.

The uninstrumented unsorted16 runtime proposal has already failed its separate qualification and is not combined with this candidate. No all-peer speed claim, no omitted full output/rollback/index/FTS/embedding work, no altered runtime tuning and no production rollout.
