# Native INSERT 100k CPU discovery

The qualified public six-peer run retained one loss: Lin 259.957 ms versus DuckDB 230.341 ms at native INSERT 100000. Shared row keys improved bulk INSERT 10k by about 5% but retained other regressions. This profile selects the next runtime optimization from observed CPU work.

Compile the existing standalone lin-peer-worker package with the same default Lin features, Rust 1.96.0, release optimization, plus explicit force-frame-pointers=yes and debuginfo=1. The actual worker source (not only its examples include! wrapper), all runtime sources, Cargo inputs, derive crate and workflow are frozen. The worker dataset, limits, timers and query path are unchanged. Standalone package selection avoids unrelated root-package dev-dependencies; its instrumented binary is not assumed equivalent to the earlier peer executable.

Run the existing worker test for the default AST quota, exact 100k-row data and default embeddings. Execute twelve fresh-database insertion samples unprofiled and twelve under user CPU-clock sampling at 499 Hz, on the same instrumented ELF. Independently validate all six fields of all 100000 result rows in both responses, ten bounded statements inside the public memory transaction, and immutable binary/source hashes. Retain raw perf.data, full callchains, report, response data, compiler and perf readiness.

This is CPU discovery only. Whole-worker samples also contain preparation, result validation, serialization and destruction outside the native operation timer. Analysis must distinguish insert_bulk/embedding/index/FTS callchains from those other phases; whole-process percentages are not automatically timed-region percentages. Frame-pointer flags and perf can perturb performance. The two timing sets quantify observed profiling variation but are not DuckDB comparisons or adoption evidence. No production limits, feature behavior or acceptance gates are relaxed. If perf is unavailable, retain that failure rather than fabricate a profile.
