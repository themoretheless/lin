# Exact cardinality: CPU tradeoff diagnostic; not accepted for rollout

Extracted the exact original/candidate BitSet implementations from the frozen index sources. Separate optimized rustc binaries use the same harness; baseline and A/A control use the identical executable. No production source changed. Twelve rotated A/A/B rounds, two six-round series,132 cases,36 processes,38016 measured observations plus9504 retained warmups. Each case has ten samples (first two warmup),2048 count/emptiness/toggle iterations or64 logical operations per sample. Input fixture construction, cloning, validation and destruction are outside the operation interval. Toggle measures insert+remove pairs. Operand orders and unequal capacities are explicit.

This is a component diagnostic on macOS ARM64, not a predeclared full-engine acceptance gate. Case order within a process is fixed, roles rotate; unrelated host activity is uncontrolled. Timings are amortized hot-loop ns/operation (toggle pair), not isolated request latency. Count uses black_box on the input reference and output. No setup/drop cost has been removed from any production engine benchmark. Independent raw audit confirms all case/sample coordinates and recomputes all medians/A/A values.

## Result

Cached count is faster in every case-series: median gain91.064%, range63.052%..99.980%. This does not justify global adoption. Median toggle gain is-79.284%, plain OR-83.200%, reverse OR-37.295%; reverse OR followed by count still has median gain-11.275%. AND outcomes depend on operand length and whether count is consumed. Metadata grows: BitSet32→40bytes and the matching Standard(Vec)/Bitmap enum32→40bytes, including standard variants. These are type sizes, not measured process RSS.

For dense65536-bit sets, count is about91.8/92.2ns baseline versus0.305ns cached across the series; toggle1.28/1.36ns versus2.28/2.37ns per pair; OR82.8/83.7ns versus152.0/157.1ns. Large sparse reverse OR+count is roughly6.02/6.01us versus6.66/6.68us. Relative toggle loss is large but its absolute per-pair penalty is around1ns; component ratios alone cannot determine full-engine net impact.

Keep this candidate out of production. Before any broader decision, reduce OR bookkeeping work (current candidate counts both old and resulting words) or measure a query-local count cache that avoids per-posting layout growth, then run appropriate read/write/Full-durable controls. Such alternatives are separate hypotheses, not measured wins. This run neither proves full-engine regression nor closes the SQLite or eight-peer objective.
