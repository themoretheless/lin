# Tail-word cardinality: layout-preserving correctness prototype

Separate hypothesis after the inline-cardinality full-engine gate failed. Preserve the original BitSet shape(Vec<u64>,usize capacity), storing exact cardinality as a final service word in the bit buffer. All positional reads, mutation loops, enumeration, AND/OR and growth exclude that word. Logical capacity/can_hold semantics are preserved, including partial final words. Growth resizes before clearing old metadata, so allocation failure cannot first erase the existing count. OR retains the one-popcount newly-added-bit formula. Public Row and persistence formats are unchanged.

Original BTreeSet oracle:14336 state transitions for baseline and candidate. Candidate library/exec/partial-index/grouped-count/transaction suite:192 passed,2 ignored. Additional differential test compares the original BitSet implementation against the candidate through28672 transitions, including exact can_hold behavior, growth, asymmetric and empty AND/OR, clone, enumeration and membership. Deliberately omitting clearing the old metadata word after growth is caught. Raw test/mutant logs retained; all production source SHA256 restored.

112 compiled layout/storage observations confirm BitSet32bytes and matching Standard(Vec)/Bitmap model32bytes in both baseline and candidate, whereas the earlier inline-cache prototype had40bytes. Logical capacities/counts agree. This does not eliminate memory overhead: every bitmap now allocates one extra u64, an initially zero-capacity bitmap now allocates8bytes, and Vec geometric growth/allocator rounding can change reserved capacity by more than8bytes. layout.json separately records buffer length and reserved capacity; these are not RSS or physical allocator-footprint measurements. Standard posting variants no longer inherit an8byte enum-layout increase.

Performance is unmeasured. Additional indirection, metadata migration and updated word bounds can regress writes or scans. Next: same CPU diagnostic with original and inline-cache controls, all losses retained; if justified, fresh full-engine COUNT, native/Full-durable write and peer controls. This candidate is not production code, not an accepted acceleration and not evidence of all-eight-peer superiority.
