# Full-sync single-row mutation coverage

This is an experimental benchmark extension, not a production source change or a performance qualification. It closes a coverage gap in compare.rs: native UPDATE/DELETE/commit/rollback do not measure durable commit latency.

24 new cases: four operations (autocommit UPDATE of indexed wing, autocommit DELETE, explicit UPDATE+commit, explicit UPDATE+rollback), two fixture sizes (1k/10k), three configurations (Lin explicit SyncMode::Full, SQLite synchronous=FULL with journal_mode=DELETE, SQLite synchronous=FULL with journal_mode=WAL). SQLite modes are separate cases; neither may be omitted when reporting peer results. SQLite default WAL autocheckpoint policy remains unchanged. WAL rollback is not an acknowledged persistent write and must not be presented as such.

Same existing docs fixture and indexed fields, same prepared single-row mutation functions, same CAS contract and handle destruction as native cases. Fresh seeded on-disk database per input; schema, seed writes, prepared statement construction, oracle snapshot, readback, reopen and input destruction excluded from measured time. Mutation function and its temporary outputs retain native timing boundaries. All directory cleanup follows connection/Db destruction. Cases use bench_checked's independent fresh validation operation before calibration and after measurement: these are sampled fixture validations, not readback of every measured iteration.

Lin oracle captures all stored fields, including generated hash and embedding, as JSON before timing; the oracle retains no Row/Cell ownership during execution. Expected result is independently patched/removed/no-op. Text and SmallText are normalized to their public text value; other Cell variants retain tagged serialization. All rows and values must match after clean close and reopen, ignoring collection order. SQLite expected rows are built directly from source Doc values and compared on all six SQL columns after close/reopen. SQLite synchronous and journal pragmas are asserted before timing.

Positive smoke: 24 isolated processes, one observation/one operation each. These samples are correctness smoke only, never performance evidence. Fault sensitivity: a separately built compare-fault.rs skips UPDATE/DELETE while falsely returning one affected row, changes commit to rollback, and rollback to commit. All 24 cases must fail at the full-value reopen oracle. Expected assertion output can be very large; retain first 8192 bytes plus full output SHA256 and byte count. These fault binaries must never be used for performance measurement.

Limitations: clean reopen is not process-kill/power-loss crash proof, not a cross-engine guarantee of identical storage implementations, and not all-peer qualification. No Lin-vs-SQLite victory is claimed from this smoke. Before accepting optimization, use same-run baseline/control/candidate pairs, repeated process series, raw timing/resource records, all native/read controls and both SQLite durable modes. Integrating this extension in an accepted benchmark requires qualification of the resulting final binary. Production public Row remains unchanged.

The first build failed because pinned bench_checked takes an immutable validation input. The corrected fixtures use RefCell only for out-of-timing ownership transfer; timed functions use RefCell::get_mut, not a dynamic borrow. The original compiler diagnostic is preserved in build-first-failure.log.
